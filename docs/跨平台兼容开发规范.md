# 跨平台兼容开发规范

> 来源：issue #10（Windows 实测 5 问题）修复沉淀——3 个 P0/P1 均为同一类根因（POSIX 分隔符假设 / npm 子进程调用语义 / 退出码吞错），文档化防止复发。
> 关联：GUIDE.md（用户行为说明）、DEVELOPMENT.md（sync 机制细节）
> 生效版本：v0.3.20+

---

## 1. 路径规范化强制（normalizeRelPath 单入口）

**规则**：所有参与比较、白名单、hash key 的相对路径，**必须先经 `normalizeRelPath()` 统一为 POSIX 格式（反斜杠→正斜杠）**，再做规则匹配或存储。

```typescript
import { normalizeRelPath } from "../lib/path-normalize";

// ❌ 禁止：直接对原始 relPath 做分隔符敏感匹配
if (relPath.includes("/plans/")) { ... }

// ✅ 强制：先 normalize
const rp = normalizeRelPath(relPath);
if (rp.includes("/plans/")) { ... }
```

**原因**：Windows 下渲染路径使用反斜杠（`\plans\a.md`），分隔符敏感的正则/字符串匹配会静默失效——曾导致 `sync --patch` 保护目录（plans/specs/reviews）被覆盖、`stack set` 假成功。

**适用场景**（不全）：
- `sync --patch` 的 PATCH_GUARD 白名单匹配（`isUserData`）
- `stack set` 的 stack 相关文件筛选
- `.add-coder-hash.json` 的 key 读写（**读取时**必须 normalize，兼容旧 Windows 反斜杠 key）

## 2. 子进程调用强制（runCommand 单入口）

**规则**：**禁止裸 `spawnSync`/`execSync` 调用 CLI 命令**，一律走 `runCommand()` 单入口（src 层 `src/lib/run-command.ts`；模板层 `templates/core/scripts/mcp-server/shared/run-command.ts`）。

```typescript
import { runCommand } from "../lib/run-command";

// ❌ 禁止：spawnSync("npm", ["prisma", "init"]) —— Windows 下 npm 为 .cmd，ENOENT → status=null 静默失败
// ❌ 禁止：spawnSync("which", ["pg_dump"]) —— Windows 无 which
// ✅ 强制：
const r = runCommand("npm", ["exec", "prisma", "--", "init"], { cwd: projectRoot });
if (r.status !== 0) throw new Error(`prisma init 退出码: ${r.status}`);
```

**runCommand 语义**：
- win32 下 `npm/npx/pnpm/git` 自动追加 `.cmd`（CreateProcess 无法直接执行批处理）
- 命令不存在（ENOENT）→ 抛「命令不可用: xxx（平台: ...）」，**不再静默 status=null**
- 返回 `{ status, stdout, stderr }`；status 为 null 时调用方必须按失败处理（`null !== 0`）
- 参数必须为数组且全部内部构造，禁止拼接用户输入进 shell

**命令语义（npm 场景）**：
- 执行包命令：`npm exec <pkg> -- <args>`（pnpm 场景维持 `pnpm dlx <pkg> <args>`）
- 安装依赖：`npm install <pkgs>`（无需 exec）
- 存在性探测：`commandExists(cmd)`（win32 内部用 `where`，POSIX 用 `which`）

## 3. 环境变量传递

**规则**：禁止 shell 内联 env 语法（`FOO=bar cmd`），一律用 `spawnSync/runCommand` 的 `env` 对象参数。

```typescript
// ✅ 强制（跨平台）：
runCommand(cmd, args, { env: { ...process.env, DATABASE_URL: url } });
// ❌ 禁止：spawnSync("FOO=bar cmd", ...) 或 shell 内联
```

**原因**：shell 内联语法是 POSIX 专属，Windows cmd/PowerShell 不识别——这是 cross-env 存在的唯一理由。本项目全部使用 env 对象传递，**不引入 cross-env**（零运行时依赖原则）。

## 4. bash 依赖边界（P2 已知项）

**现状**：
- `init.ts` 中 `db-ensure.sh` 通过 `runCommand("bash", ...)` 调用——Windows 无 bash 时**失败已被检测**（非零退出码 + 「治理模型未就绪」），但功能不可用
- `templates/.../mcp-server/shared/fs.ts` 的 doc-format-guard 同理——失败显式返回 guard 失败

**后续评估条件（满足任一即启动 P2）**：
- 需要替代 db-ensure.sh 的管道/重定向/条件逻辑 → 评估 shelljs 或纯 Node 重写
- 需要更复杂 spawn 语义（流式/超时分级）→ 评估 execa
- **在引入前**：必须先更新本规范 + 走 HITL 依赖决策

### 4.1 模板加载机制（P2 独立课题，2026-08-07 登记）

**课题**：`templates/.../mcp-server/shared/prisma.ts` 用 `createRequire(import.meta.url)` 同步加载 `src/generated/prisma/client.ts`——vitest 测试环境下 Node 22 `require(esm)` 按 ESM 解析生成物时，其内部无扩展名 import（`./enums`）解析失败（18 个 pre-existing 测试失败根因）。

**影响范围（已核验，非常窄）**：**仅 vitest 测试流程**（4 个测试文件 18 个用例）。
- MCP 运行时经 `mcp.json` 的 `command: "tsx"` 启动（tsx loader 解析无扩展名 import，实验验证 TSX_OK）——不受影响
- CLI（bin）为 dist 打包产物，无 src/generated 依赖——不相关
- 14 个模板消费方（tools/resources/notifications/tasks/gateway）全部运行在 tsx 下，无 node 直跑路径

**背景**：`createRequire` 替代 `await import()` 是 2026-07 有意决策（见 mcp-restructure-plan：同步加载 + CJS/ESM 双兼容）。运行时（tsx）不受影响，仅测试环境受限。

**候选方案**：`import()` 动态导入替代 createRequire（vitest 可 transform 解析），需权衡：
- 同步加载语义变化（prisma.ts 顶层导出 `prisma` 实例，改异步需调所有消费方）
- CJS/ESM 双兼容验证（消费方含 tsx 运行的 MCP server）
- 触发条件：需要测试环境全绿（除 pre-existing 18 项外新增测试受影响）或 Prisma 生成物格式变更
- 优先级：**低于 bash 替代**（本课题仅影响测试全绿，bash 影响真实用户功能）
- **启动前**：更新本规范 + 走 HITL 决策，核验 mcp-restructure-plan 的原始决策背景
- **收敛状态（2026-08-07）**：登记完整、影响范围已核验（仅 test 流程）、优先级已明确（低于 bash 替代）——确认**暂不实施、保持登记**，不因测试全绿诉求破坏 createRequire 的同步加载有意设计；触发条件满足时再启动

## 5. hash 全量基线语义

**规则**：`.add-coder-hash.json` 是**完整渲染结果的全量基线**，不是本轮差异快照。

- 保存 = 旧 hash 全量保留 + 本轮处理后**磁盘当前内容**刷新（新建/覆盖/跳过均以磁盘为准）
- 用户 `[a]` 跳过保留其修改 → hash 记录用户版本 → 下一轮不再误判冲突
- 读取时 key 必须 normalize（兼容旧 Windows 反斜杠 key）
- 版本升级/首次 patch 时全量重写基线（既有 isFirstPatch/isUpgrade 逻辑）

## 6. 失败语义（禁止"假成功"）

**规则**：
- `init` 只有在 `db push + generate` 双成功后才返回成功；任一失败 → 「✗ 治理模型未就绪: 原因」+ 非零退出码
- `stack set` 写后断言：profile 文件（`.add` + magicDir 双路径）与 `project_rules.md` 引用行未写入 → 失败
- `status` 缺失文件 → 非零退出码（CI 门禁可用）
- 所有子进程退出码必须检查（`status !== 0`，含 null）
